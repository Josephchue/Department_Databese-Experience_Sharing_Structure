# 部署说明

本文件说明如何把知识库 API 部署到部门服务器并保持常驻运行。

面向对象：接手部署的人。假定此前没写过 systemd 单元，但会 SSH、会敲命令行。

> **本文件不含服务器地址、账号、密码。** 这些属于基础设施信息，
> 仓库是公开的，一律不写进来。需要的值在交接文档和群公告里。
> 下文中用 `<服务器地址>`、`<共享账号>` 这样的占位符表示。

---

## 一、部署前必须知道的几件事

### 1.1 谁能干什么：两个账号，靠一条组权限共享

服务器上跟我们有关的是两个账号（真名见交接文档）：

- `<共享账号>` —— 我们 SSH 进去用的那个。**没有 sudo**。
- `<服务账号>` —— 知识库专职服务用的账号，shell 是 `nologin`，
  **我们登不进去**（这是设计，不是故障）。

`<共享账号>` 在部署目录所属的组 `<共享组>` 里，所以对 `<部署目录>` 可读可写。
这一条决定了很多事：**传代码、改配置、跑验证都不需要 sudo**，
只有动 systemd 才要服务器管理员。

| 操作 | 能不能做 |
|---|---|
| 把代码写进 `<部署目录>` | 能（靠组权限，不需要 sudo） |
| 建虚拟环境、装 Python 包 | 能 |
| 借一个空闲端口起份临时实例做验证 | 能，不影响正式服务 |
| `systemctl restart scitech-kb` | **不能**——没 sudo，也没配 polkit 规则 |
| 单元放进 `/etc/systemd/system/`、`daemon-reload` | **不能**，要找服务器管理员 |
| 改数据库的系统级配置 | **不能**，要找服务器管理员 |

所以**第一次上 systemd 必须和服务器管理员配合**（第五节）；
日后更新代码不用（第九节）。

### 1.2 服务器上已经跑着别的服务

同一台机器上还有 QQBot 组的服务。动手前先确认真实占用的端口，
不要凭印象挑——撞了端口不会有人提醒，只会有一个服务起不来。

```bash
ss -tlnp | grep LISTEN
```

2026-09-22 在 M710q 上实测到的情况：

| 端口 | 谁占着 |
|---|---|
| 8000 | **知识库自己**，单元里绑的是 `127.0.0.1`（只本机可达，见第九节） |
| 8080 | 别人的服务，**不要动** |
| 8001 | 空闲。想临时起一份实例做验证就借它，不影响 8000 上跑着的那份 |

8000 上跑着的就是正式服务，不需要换端口。**要让它能从校园网访问，
改的是绑定地址（`--host 127.0.0.1` → `--host 0.0.0.0`），不是端口**——
只改绑定，端口保持三处（本文件、`scitech-kb.service`、`.env` 的 `API_PORT`）一致。

### 1.3 数据库是 MariaDB，单元名叫 `mariadb.service`

```bash
systemctl list-units --type=service --all | grep -iE "maria|mysql"
```

2026-09-22 实测结果：**`mariadb.service`**（MariaDB 10.11.14），
这台机器上**没有** `mysql.service`。
`scitech-kb.service` 的 `After=` 必须写这个名字，写错了服务照样"能起来"，
只是少了等数据库就绪那层保护——静默失效，最费时间的一类问题。

### 1.4 数据只在本机

MySQL 建在这台服务器上，向量库落盘在项目的 `data/` 目录。
两处都是**真实数据**，都不能进 Git，迁移和备份都要单独处理（见第六节）。

## 二、目录约定

```
<部署目录>/                           <- 代码，从 Git 克隆
├── .git/                             <- 是个 git 仓库，remote 指向 GitHub
├── .venv/                            <- 虚拟环境，服务器上现建
├── .env                              <- 数据库密码 + 写接口口令，权限必须 600
├── data/                             <- 向量库落盘，真实数据
├── .cache/huggingface/               <- 向量模型缓存，约 100MB
└── ...
```

`data/`、`.cache/`、`.env`、`.venv/` 都不进 Git，属于本机运行产物。

部署目录**不归 `<共享账号>` 所有**（属主是 `<服务账号>`，靠组权限共享）。
所以别在里面折腾属主，也别指望改完文件属主不变——见 9.5。

## 三、手工跑通（先做这一步）

**不要一上来就配 systemd。** 先在命令行里把服务跑起来，
确认能跑通，再交给 systemd 托管。反过来做的话，
服务起不来时你分不清是代码的问题还是单元文件的问题。

### 3.1 放代码、建环境

```bash
# 部署目录归服务账号、靠组权限共享；克隆前先确认自己有写权限
git clone <仓库地址> <部署目录>
cd <部署目录>

python3 -m venv .venv
source .venv/bin/activate
pip install -i https://pypi.tuna.tsinghua.edu.cn/simple -r requirements.txt
```

依赖里有 PyTorch，装完约 1–2 GB，视网络情况要几分钟。

### 3.2 配 .env

```bash
cp .env.example .env
chmod 600 .env
vim .env
```

`chmod 600` 不是可选项：这个文件里有数据库密码，
权限放开等于把密码给机器上所有用户看。

填 `DB_HOST`（本机就是 `localhost`）、`DB_USER`、`DB_PASSWORD`、`DB_NAME`。

### 3.3 建库、造数据

```bash
python -m scripts.init_db      # 建库建表，建出 7 表 2 视图
python -m scripts.seed         # 造演示数据，用来验证服务是通的
```

第一次跑 `scripts.seed` 会下载向量模型（约 100MB），要等一会儿。

> 演示数据是**假数据**（测试员甲、测试员乙…）。
> 真实成员数据走数据管道线导入，不要手改 `scripts/seed.py`。
> 上线前想清空演示数据，跑 `python -m scripts.reset_db` 再导入真实数据。

### 3.4 起服务，验证

```bash
python -m uvicorn api.main:app --host 127.0.0.1 --port 8000
```

**启动要等 20–30 秒**（要加载向量模型）。看到日志里出现
`Application startup complete` 才算好。另开一个终端：

```bash
curl -s http://127.0.0.1:8000/api/health
```

验收标准：返回的 JSON 里 `ok` 为 `true`，经验条数为 8，向量维度为 512。

再试一条检索，确认向量库真的能用：

```bash
curl -s "http://127.0.0.1:8000/api/experience/search?q=设备出故障了咋办"
```

验收标准：返回若干条，第一条是「投影仪不亮」那条。

到这里为止都是你自己的账号就能完成的。确认没问题再往下。

## 四、本文件为什么不用 systemd 的 EnvironmentFile

需求文档里提到过，密钥应该改成用 systemd 的 `EnvironmentFile` 注入。
那个建议针对的是 LLM key。**这里不照搬**，原因是两者格式不兼容：

`python-dotenv` 认识 `KEY="v#1"` 这种写法（引号、井号都处理），
systemd 的 `EnvironmentFile` 不认——它会把引号当成值的一部分、
把井号当普通字符，于是密码里只要有一个引号或井号，连库就会失败，
而报错是关于认证的，查半天查不到配置格式上。

所以这里的做法是：**继续用 `.env` + `chmod 600`**，
靠文件权限保护，不靠 systemd 注入。

如果以后要上更严格的做法，正确方向是 systemd 的 `LoadCredential=`，
而不是 `EnvironmentFile`。

## 五、交给 systemd 托管（需要服务器管理员配合）

把 `/etc/systemd/system/` 下的操作整理成一段能直接发给服务器管理员的话：

> 需要新增一个服务单元 `scitech-kb.service`，内容见
> `<部署目录>/deploy/scitech-kb.service`。
> 需要：
> 1. 把该文件复制到 `/etc/systemd/system/scitech-kb.service`
> 2. `systemctl daemon-reload`
> 3. `systemctl enable --now scitech-kb`
> 4. 给共享账号配一条 polkit 规则，允许它
>    `systemctl start/stop/restart/status scitech-kb`
>    （参照已有的机器人服务那条规则）
>
> 代码目录 `<部署目录>` 的属主是 `<服务账号>`、组是 `<共享组>`，
> 我们（`<共享账号>`）在组里，后续更新代码我们自己来，不需要再麻烦你。

> **这一节是"从零上 systemd"的走法，这台服务器上已经做完了。**
> 现在实际是什么形状、还差哪一步，直接看第九节。

服务器管理员做完之后，只读的操作能自己来；
**改完代码要重启，还是得找管理员**（没配 polkit 规则就是没配）：

```bash
systemctl status scitech-kb          # 能看
systemctl restart scitech-kb         # 不能，要管理员
```

> ⚠️ `journalctl -u scitech-kb` 要看别人的服务日志，得在
> `systemd-journal`（或 `adm`）组里。不在组里时它**不报错**，
> 只回一句 `-- No entries --`——看着像"这服务从没跑过"，
> 其实只是没权限看。这句话很容易把人带偏。

### 5.1 万一暂时等不到服务器管理员

可以先用用户级 systemd 顶一阵：

```bash
mkdir -p ~/.config/systemd/user
cp deploy/scitech-kb.service ~/.config/systemd/user/
# 把 [Service] 里的 User= / Group= 两行删掉——用户级服务不需要，写了反而报错
systemctl --user daemon-reload
systemctl --user enable --now scitech-kb
loginctl enable-linger <共享账号>    # 这步通常也需要权限，同样要找服务器管理员
```

用户级服务只在用户登录期间存活，`enable-linger` 才能让它在没人登录时也跑。
而 `enable-linger` 一般还是要权限。所以这只是过渡，不能当最终方案。

## 六、备份与迁移

需求文档的验收标准里有一条：**数据落盘可迁移，换机器只拷数据目录。**
要满足它，需要备份三样东西：

| 备份什么 | 在哪 | 怎么备 |
|---|---|---|
| 结构化数据 | MySQL | `mysqldump -u <用户> -p scitech_kb > 日期.sql` |
| 向量库 | `data/chroma/` | 直接打包整个目录 |
| 向量模型缓存 | `.cache/huggingface/` | 可不备，新机器会重新下（约 100MB） |

```bash
# 例：打一份备份到自己的家目录
mkdir -p ~/kb-backup
mysqldump -u <用户> -p scitech_kb > ~/kb-backup/scitech_kb-$(date +%F).sql
tar czf ~/kb-backup/chroma-$(date +%F).tar.gz data/chroma
```

> **备份文件里是真实数据。** 存在服务器本机没问题，
> 不要下载到个人电脑、不要传网盘、不要发群里。
> 另外需求文档写明服务器的数据盘目录（`/data/`）不归技术组使用，
> 备份不要往那里放。

**恢复**（新机器上）：

```bash
mysql -u <用户> -p < 备份的.sql        # 1. 恢复结构化数据
# 2. 把解压出的 chroma/ 放回项目 data/ 目录下
# 3. .env 照原样配好（里面有数据库密码，不在备份里，要单独拿到）
```

`.env` 不在 Git 里，也不在上面任何一份备份里——迁移时要单独、安全地传。

### 6.1 定期备份

建议每周一次，用 cron 挂在家目录下：

```bash
crontab -e
# 每周一凌晨 4:10 备份
10 4 * * 1 cd <部署目录> && ./deploy/backup.sh
```

`deploy/backup.sh` 需要自己写——本仓库暂不提供，
因为备份路径和保留策略取决于服务器实际情况。
写的时候注意两点：**备份目录要有权限保护**（真实数据），
**要清理过期备份**（否则会一直涨）。

> 注意：备份脚本会用到数据库密码。
> 不要把密码写在脚本里——脚本要进 Git，密码不能进。
> 从 `.env` 里读，或者用 MySQL 的 `~/.my.cnf`（权限 600）。

## 七、常见问题

| 现象 | 原因 | 怎么处理 |
|---|---|---|
| `Application startup` 之后很久没动静 | 正在加载向量模型，正常 | 等 20–30 秒。别急着判断为挂掉 |
| `Can't connect to MySQL server` | 数据库没起 / 密码错 / 主机写错 | 确认 MySQL 在跑；核对 `.env` 三项 |
| `Table 'member' already exists` | 重复建表，schema 不是幂等的 | 本地数据不要了就 `scripts.reset_db`，要的话别重复建 |
| 服务起来但 8000 端口连不上 | 绑的是 127.0.0.1 | 本机 curl 才能通，这是有意为之，见单元文件注释 |
| 改了 `.service` 没生效 | 忘了 `daemon-reload` | `systemctl daemon-reload` 后重启。**这步不会报错，只会静默不生效** |
| 单元起不来，报看不懂的权限错 | 加固那几行限制太紧 | 注释掉 `ProtectSystem` / `ProtectHome` / `ReadWritePaths` 再试 |
| 首次启动卡在下载模型 | 服务器访问不到 HuggingFace | `api/config.py` 里已设 `HF_ENDPOINT` 走镜像；确认服务器能出网 |
| 下模型**不动**——不报错，进度就是不往下走 | HuggingFace 的 xet 协议国内不通 | `api/config.py` 里已设 `HF_HUB_DISABLE_XET=1` 关掉它。**这两个变量都必须在 `huggingface_hub` 被导入之前设好**，临时 export 无效 |

## 八、部署验收标准

全部满足才算部署完成：

1. `systemctl status scitech-kb` 显示 `active (running)`。
2. `curl http://127.0.0.1:8000/api/health` 返回 `ok: true`，经验 8 条，维度 512。
3. 语义检索「设备出故障了咋办」能召回「投影仪不亮」那条。
4. 服务器重启后服务自动起来（`systemctl is-enabled scitech-kb` 为 `enabled`）。
5. `journalctl -u scitech-kb` 里有日志，能看出服务在干什么。
6. 服务器上有一份可用的数据备份，且知道怎么恢复。

## 九、服务器上现在的实际形状（2026-09-22 实测）

前面八节是**从零部署**的走法。这一节记的是这台服务器上**已经落地**的形状，
接手的人先看这里，能省掉很多试错。

### 9.1 服务的身份：一个专职服务账号

服务**不跑在 `<共享账号>` 名下**，而是跑在一个专职的 `<服务账号>` 名下：

| | 谁 | 能登进去吗 |
|---|---|---|
| 我们操作用的账号 | `<共享账号>` | 能（就是 SSH 进去那个） |
| **跑服务的账号** | `<服务账号>` | **不能**，shell 是 `nologin` |

服务账号不能登录是**设计**，不是故障：它只用来跑服务，
被攻破也拿不到一个能登进来的 shell。
代价是我们没法"切到它名下"做任何事，只能靠文件权限。

### 9.2 目录形状

```
<部署目录>/                     <- 属主 <服务账号>:<共享组>，权限 2770
├── .git/                       <- 是个 git 仓库，remote 指向 GitHub
├── .venv/                      <- 已建好
├── .env                        <- 600，属主 <服务账号>
├── data/chroma/                <- 向量库落盘，**真实数据，别覆盖**
└── .cache/huggingface/         <- 模型缓存，由单元的 HF_HOME 指到这里
```

`2770` 里那个 `s`（setgid 位）不是装饰：它让目录里**新建**的文件
自动归到 `<共享组>`。这正是"一个账号部署、另一个账号运行"能成立的前提。

### 9.3 单元里那几个环境变量，每一个都有原因

```ini
User=<服务账号>
Environment=PYTHONUNBUFFERED=1
Environment=HF_HOME=<部署目录>/.cache/huggingface
Environment=HOME=/var/lib/<服务账号>
```

- `PYTHONUNBUFFERED=1`：不加的话，stdout 重定向到文件时是块缓冲，
  启动时那几行关键日志（尤其是"鉴权已启用 / 未启用"）要等缓冲满了才出现，
  看着像卡死。
- `HF_HOME`：不指到这里，模型会去服务账号的 home 找，找不到就联网重下
  （约 100MB），每次重启都白等。
- `HOME=/var/lib/<服务账号>`：服务账号的 home 不可写，而 git 要写
  `~/.gitconfig`（自动部署里要设 `safe.directory`）。给它一个可写的 HOME，
  否则自动部署会以 `dubious ownership` 失败。

### 9.4 自动部署每 5 分钟跑一次，规则要记住

`auto-deploy.timer` 每 5 分钟触发 `auto-deploy.sh`，脚本逻辑是：

```
git fetch  →  比对 HEAD 和 origin/main
  ├─ 一样         → 静默退出，什么都不做
  ├─ 工作区有改动  → 记一行"工作区有未提交改动，跳过本次部署"然后退出
  └─ 有新提交且工作区干净 → git merge --ff-only  →  重启服务
```

★ 最后一步是**重启服务**，而重启要重新加载模型（20–30 秒）。
所以：**只要 HEAD 和 origin/main 不一致、工作区又是干净的，
服务就会每 5 分钟被重启一次**，页面隔几分钟卡一次。
在服务器上放"还没 push 的代码"，必须避开这个状态。

**安全的状态是：让 HEAD 停在 `main`，改动只放在工作区。**
这时比对结果是 `HEAD == origin/main`，脚本走第一个分支静默退出，
连"工作区有改动"那行都不会记。

### 9.5 谁的手能碰什么（2026-09-22 实测）

| 想做的事 | 结果 |
|---|---|
| 读写 `<部署目录>` 里的文件 | **能**（在组里，不需要 sudo） |
| 用现成的 `.venv` 跑服务、跑验证 | **能**（借个空闲端口起临时实例，不影响正式服务） |
| 重启 `scitech-kb.service` | **不能**——`sudo` 要密码，也没配 polkit 规则 |
| 改 `/etc/systemd/system/` 下的单元 | **不能** |
| 读 `.env` | 能读；但属主是别人，所以**写不了**——要改值得删掉重写一份 |
| 把文件属主改回服务账号 | **不能**——`chown` 要 root |

最后两条合起来有个副作用，一定要知道：
**我们在部署目录里新建或覆盖的文件，属主会变成 `<共享账号>`。**
服务账号靠组权限仍然读得到，所以服务照常跑；
但别再指望"部署目录里属主统一"这件事——`chown` 我们自己做不到。

### 9.6 还差的这一步要服务器管理员做

单元已经装好并常驻运行了，只差一处：

> `scitech-kb.service` 的启动命令现在是
> `uvicorn api.main:app --host 127.0.0.1 --port 8000`——只监听回环，
> 校园网里访问不到。请把 `--host 127.0.0.1` 改成 `--host 0.0.0.0`，
> `daemon-reload` 后 restart 一次。
>
> 顺便请确认 `<部署目录>/.env` 里已经有 `KB_SHARED_PASSWORD`（页面的口令，读写都要）。
> 服务重启后第一屏日志会明说鉴权是"已启用"还是"未启用"——
> 看到"未启用"就先别绑出去。

`0.0.0.0` 之前必须配好口令，理由见 `api/config.py` 里那段注释：
这道口令是**部门共享**的，它只回答"能不能进"、不回答"是谁"，
绑出去之后部员都能看能改——要真身份得上学校 CAS。
